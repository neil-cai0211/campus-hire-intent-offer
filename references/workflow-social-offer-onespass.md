# 链路二B-补 · 社招 offer 一站式脚本（offer-onepass-social.js）

> 2026-11-03 实战沉淀。某社招候选人（初级技术支持专员 / 技术支持组 / S1 / 试用期 6 个月 / 邮箱中途被改过）
> 一次跑通：填表 → 校验 → 预览 → 选模板 → 插图 → 校验正文 → 发送 → 确认。

## 为什么需要一站式脚本

**草稿不保存**。填表、选模板、插图、正文校验、发送必须**在同一次页面会话内连续跑完**。
中间任何一次 `goto` / `reload` 都会丢失全部未提交内容。

所以拆成两个脚本（先填表、后发送）**行不通** —— 必然要重新填一遍。
必须一个脚本从头跑到尾。

```bash
node offer-onepass-social.js <配置.json>          # 只填表 + 校验（不发）
node offer-onepass-social.js <配置.json> --send   # 全流程 + 发送
```

脚本：`$HIRE_SKILL_DIR/scripts/offer-onepass-social.js`

```json
{
  "resumeId": "<32位hex>",
  "email": "<候选人邮箱（以系统里候选人联系邮箱为准）>",
  "position": "初级技术支持专员",
  "jobCategoryOrder": ["营销", "技术", "职能", "管理"],
  "rank": "S1",
  "rankSeqOrder": ["营销序列-S", "专业序列-P", "技术序列-T"],
  "probationMonths": 6,
  "onboardDate": "2027/07/01",
  "subject": "福州誉龙智能科技有限公司",
  "reportAddress": "福建省福州市鼓楼区火炬高新技术创业园1号楼",
  "cityProvince": "福建省",
  "city": "福州市",
  "leader": "<汇报对象姓名>",
  "pay": {
    "prob": { "basic": 4800, "secret": 300, "perf": 0 },
    "full": { "basic": 4800, "secret": 300, "perf": 900 }
  },
  "offerValidDays": 3,

```

- `leader` 是**姓名**（不是职位），用于联想搜索。
- `pay.prob.perf = 0` 要**显式写 0**（试用期不发绩效），系统接受 0。
- `img` 必须指向**当前**意向书 PDF 渲染出的插图（见 pitfalls 的「时效校验」）。

## 关键实现要点（都是踩出来的）

### ① 页面状态污染 ⇒ 每次运行必须重新 goto

上一次运行如果停在**预览态**（草稿不保存，但页面 DOM 留在预览态），
下一次运行的字段定位会**全部失效**（label 变重复、薪酬区收起）。

脚本开头无条件 `goto` + 检测残留预览态。

### ② ⚠ 预览后 label 文本会重复 —— 定位必须用「最近的 .el-select」

预览后 label 从 `入职岗位：` 变成 `入职岗位 入职岗位：`（重复）。
⇒ 精确匹配 `innerText === '入职岗位'` **匹配不到**。

而且**不能靠「向上找祖先 → 找里面的 input」**来取值 —— 祖先里可能包含别的字段的 input，
实测把「入职岗位」读成了「产品运营」（隔壁字段的值）。

✅ **唯一可靠的定位法**：遍历所有 `.el-select`，向上找最近的 `.label-name`，
取它的 `input.value`。这个方法**表单态/预览态都准**，且一一对应无歧义。

```js
for (const el of document.querySelectorAll('.el-select')) {
  let n = el, label = '';
  for (let k = 0; k < 8 && n; k++) {
    const ln = n.querySelector ? n.querySelector('.label-name') : null;
    if (ln) { label = (ln.innerText || '').replace(/\s+/g, ' ').trim(); break; }
    n = n.parentElement;
  }
  const inp = el.querySelector('input');
  // label + inp.value 一一对应
}
```

非 select 的普通 input（如 `入职日期` = el-date-picker、`offer有效期`）
另写一套 `locateInput` / `readInput`，按 label 文本找**同级容器**里的 input。

### ③ ⚠ 已有值就跳过（社招 offer 表单继承审批值）

社招 offer 表单的入职信息**大部分已由录用审批带过来**（且部分字段 `readonly`）。
- 汇报对象：`readonly: true`，值已是审批带过来的 → **不要重填**（重填会触发远程联想，失败率高）
- 入职日期 / 工作城市 / 合同主体 / 报到地址 / 试用期 / 岗位 / 职级：同样先读后判

⇒ 脚本统一「**先读，已有值且符合预期就跳过；没有才填**」。
这既快又避免「改动必审字段 ⇒ 触发重新审批」。

### ④ ⚠⚠ 顺序硬约束：先职级，后岗位

**反了会失败**：先选岗位 → 再开职级下拉时，岗位树的弹层还挂在 DOM 里，
职级下拉点不开（树节点数不对 = 8 个分类节点，没有序列节点）。

⇒ 脚本顺序固定为：**试用期 → 职级 → 岗位 → 入职日期 → 合同主体 → 报到地址 → 汇报对象 → 工作城市 → 薪酬 → offer有效期 → 抄送 → 预览 → 模板 → 插图 → 发送**。

（录用审批脚本 `fill-approval-social.js` 同样要「先职级后岗位」。）

### ⑤ 岗位树 / 职级树是两棵不同的树

| | 岗位下拉 | 职级下拉 |
|---|---|---|
| 层级 | 分类（技术/营销/职能/管理/未定义分类）→ 岗位 | 序列（管理-M/专业-P/营销-S/技术-T）→ 职级 |
| 标签取法 | `.custom-tree-node` 的 innerText | `.el-tree-node__content` 的 innerText |
| 展开方式 | 点**展开图标** | 点**文本**才展开（点图标无效） |

⚠ 组织架构树（入职部门）又不一样：标签在 `.el-tree-node__content` 的 innerText / `title`，
且**必须用 JS dispatch click**（坐标点击不落位，见 social-approval 文档）。

### ⑥ 抄送的值不在 input.value，在 `.el-select__tags-text`

抄送邮箱选中后渲染成 **tag 标签**，`input.value` 始终为空。
⇒ 读值要读 `.el-select__tags-text` 的 innerText。

候选匹配必须**精确等于姓名或以「姓名(」开头**，否则会点到「基础信息」这类容器文本。

### ⑦ 下拉选项过滤不能太严

`bb.y > 0 && bb.y < 1400` 这种视口过滤会让选项列表变空（选项可能在视口外/坐标为 0）。
⇒ 只按 `width > 8 && height > 4` 过滤；点击优先用 **Playwright locator**
（`.el-select-dropdown__item` + `filter({hasText})`），坐标点击兜底。

### ⑧ 预览 / 修改邮件按钮：locator `:visible` 会失效

这两个按钮用 `p.locator('button:visible')` 经常匹配不到。
⇒ 用「遍历按钮 → 匹配 innerText → `scrollIntoView` → 取坐标 → 点击」。

⚠ 取坐标前**必须先 scrollIntoView**，否则 y 可能超出视口（实测 y=1733 > 1400）点击落空。

### ⑨ 弹窗类按钮用坐标点，不要用 locator

「确定发送offer吗?」「必审字段被修改…」这类弹窗，按钮可能是 `span`/`div` 而非 `<button>`。
⇒ 遍历 `.el-dialog, .el-message-box, [role="dialog"]` 内的可见元素按文本找 + 坐标点。

### ⑩ 薪酬区 9 个框的顺序（实测）

```
[0] 计薪方式   [1] 试用期基本  [2] 转正后基本
                [3] 试用期保密  [4] 转正后保密
                [5] 试用期绩效  [6] 转正后绩效
                [7] 试用期合计  [8] 转正后合计
```
**按行排列**，不是按列。赋值索引是 **1~6**（不是 0~5）。
填完读 [7][8] 校验合计。

## ⚠⚠⚠ 最危险的一步：预览时弹「必审字段被修改，将重新审批offer」

**这个弹窗必须点「取消」**，不能点「确定」。

点「确定」= **发起新一轮录用审批**（审批链：发起人 → 部门负责人 → HRBP），
offer 根本发不出去。实测点过之后，卡片状态变成「录用审批 | 审批中」，
offer 环节的记录变成「已失效」。

### 触发条件

系统拿 **offer 表单当前值** 与 **录用审批留值**逐字段比对，
不一致的字段如果属于「必审字段」就弹这个框。

### 实测触发点：审批的薪酬没落库

那次**录用审批提交后薪酬是空的**（提交弹窗出现但值没存进去），
而 offer 表单有 5100/6000 ⇒ 系统认为「薪酬被改了」⇒ 弹重新审批。

⇒ **修法：让两边一致**。在**录用审批页**把薪酬填上并**「保存草稿」**
（不要点「确定」提交，那会发起审批），让审批留值 = offer 表单值。
之后再预览就不会弹这个框。

⚠ 注意 social-approval 文档里「保存草稿会清空表单」那条：实测**填完薪酬点保存草稿后重载，
薪酬是留存的**（可能是那条针对另一种情况）。稳妥做法：
填薪酬 → 保存草稿 → **重新加载页面验证薪酬还在** → 再回 offer 页发送。

### 「审批已撤销」状态也能发 offer

Neil 撤销误触发的审批后，卡片显示「录用审批 | 审批已撤销」，按钮含「重发Offer」。
此时审批页是**可编辑草稿态**，留值仍可读可改 ⇒ 照样能走「审批留值对齐 → 发 offer」。

## 判断 offer 是否真的发出去了

⚠ **不要看 offer 列表页的「offer发送时间」列** —— 那列是空的（实测已发出的王彤也是空的），
会误判成「没发出去」。

✅ **正确判据：候选人详情页右侧的 offer 记录区**，每条记录有：
- 状态（`待确认` / `已失效` / `已接受`）
- **到期时间**（如「1105到期」）
- **发起时间**（如「2026/11/03 15:43 发起」）+
  发件人（发件人本人姓名）

该候选人的三条记录（截图实证）：

| 状态 | 发起时间 | 说明 |
|---|---|---|
| 已失效 | 2026/11/02 21:25 | 第一次发（试用期 3 个月版本） |
| 已失效 | 2026/11/03 15:34 | 误点「确定」触发重新审批那次 |
| **待确认** | **2026/11/03 15:43** | ✅ 正确的重发（试用期 6 个月 / 新邮箱 / 1105 到期） |

⇒ **「到期时间」= 意向书告知有效期**，可以直接和意向书交叉验证。
`1105到期` ↔ 意向书「本通知书有效期至 2026年11月5日」✓

## 发送成功的三个独立判据

1. 卡片按钮：`发送Offer` → `重发Offer`（**弱**，撤销审批后也会变）
2. 右侧 offer 记录区出现新记录且状态为「待确认」（**强**）
3. 到期时间与意向书有效期一致（**交叉验证**）

## 邮件正文校验（插图之后、点确定之前）

必须在「修改邮件内容」弹窗**关闭前**校验，关闭后 `.wangEditor-txt` 就从 DOM 消失了。

要断言的：
- 「离职证明」「薪资证明」条款存在
- 称呼是「先生/女士」而非「同学」
- 图片数量 = 预期（意向书插图 + 附件图）
