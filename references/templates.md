### 怎么选模板

先看**固定部分比例**（这是硬约束，与薪酬口径必须一致），再比结构：

| 岗位线 | 固定部分 | 用哪套 |
|---|---|---|
| 职能 / 技术 / 研发 / 产品 / 技术支持 | 80/5/15 | `tech`（1-2 职能及技术类） |
| 销售线（含电销）、品牌营销线（平面设计师除外） | 95/5 | `sales`（1-1 销售通用类）或 `brand`（1-1 品牌营销类） |
| 平面设计师（各级） | 80/5/15 | `tech` |
| 其他未归类 | 80/5/13 | `other`（1-2 其他） |
| 驻外 / 外派销售 | 按外派方案 | `expatriate`（1-3 销售外派类） |

- `sales` 与 `brand` 固定部分相同，区别在**表述与试用期示例**（sales 6 个月、brand 3 个月），以及 brand 多了「属地」而不是「工作地点」。
- `other` 的绩效是 **13%** 不是 15%，且示例主体是成都的大客户经理 —— 用于「销售线以外但也不是标准职能技术岗」的场景。
- `expatriate` 含**约定服务期**与**签证失效条款**，只适用于驻外岗，不要用于普通销售。

⚠ **比例对不上就是填错**。若某人属于销售线却用了 `tech` 模板，意向书上的固定部分会变成 80/5/15，与审批表里的 95/5 冲突。**先确认比例，再选模板**。


## 二、技术类 vs 销售类：结构差异

| 字段 | 技术/职能类（1-2） | 销售通用类（1-1） |
|---|---|---|
| 职位 | `□职位名称：` | `职位/职级名称：`（带职级） |
| 工作地点 | `□工作地点：福建福州及您参与…`（**写死在模板里**） | `工作地点：____ 及您参与…`（**前缀留空待填**） |
| 汇报上级 | `□职位名称：VP` | `上级职位名称：____` |
| 入职日期 | `□2026年10月23日  ☑待签订劳动合同时最终确认` | `____年__月__日（入职日期待签订劳动合同时最终确认）`（**无☑**） |
| 首期合同期限 | `3年以上，终止日期为合同终止年的12月31日` | `____年以上，终止日期为合同终止年的___月___日`（**年限也留空**） |
| 固定部分表头 | `1、基本工资` / `2、保密津贴` / `3、绩效激励` | `基本工资` / `保密津贴`（**只有两项**） |
| 特别说明 | 季度绩效激励政策 | **销售岗激励政策参照《销售激励方案》** |
| 称呼段 | `____：您好！` | `____：您好！`（6个下划线空格） |
| 联系人 | HR 联系人 + 手机号（见 config.js rules.contact） | 模板原为 **销售线原联系人 / 11位号码** |

**关键差异**：技术类模板的待填位是**已有文字**（可直接Find/Replace），销售类模板的待填位**全是下划线空格**（必须字符级Range替换）。

### 合同终止日算法

入职年 + 3，取**与入职同季度的最后一天**：
- 7/1 入职（Q3）→ 合同终止年 Q3 末 = **9月30日**
- 1/31 入职（Q1）→ Q1 末 = 3月31日

### 告知有效期（必须动态，禁止写死）

**N天 = 从发送当天起算、含当天。**

例：offer表单「offer有效期」填3，10-29发送 → 10.29 / 10.30 / 10.31 → 意向书填「本通知书有效日期至 2026年10月31日」。

| 发送日 | 告知有效期至 |
|---|---|
| 10-29 | 2026年10月31日 |
| 10-30 | 2026年11月1日 |
| 12-30 | 2027年1月1日（跨年正确） |

实现：`$HIRE_WORKSPACE/valid-date.js`（工作区默认 `D:\AI-Workspace\录用意向书`）
```js
const { computeValidDate } = require('./valid-date');
const v = computeValidDate('2026-10-30');   // → {year:'2026', month:'11', day:'1', text:'2026年11月1日'}
```
跨天发送时用环境变量指定起算日：`OFFER_BASE_DATE=2026-10-30 node gen-intent.js '<cfg>'`

⚠ **意向书先于offer生成**。若意向书昨天生成、今天才发送，必须用发送日重跑意向书，否则有效期对不上。

## 四、字符下标表

完整表在 `config.js` 的 `templates.<key>.fills`（五套模板共 89 条填位）。
**机器解析出的槽位结构**在 `references/template-slots.json`（五套模板 × 62 个单元格）。

此处只记**读法**：

- `cell`：`行,列`（Word表格坐标，1基）
- `idx`：该单元格内**字符序号**（不含段落结束符与单元格标记符）
- `len`：要覆盖的字符数

**同一单元格内多项替换，必须按 idx 降序执行**（否则前面的替换会改变后面字符的序号）。已在生成脚本中统一处理：先收集所有替换点的绝对位置 → 按Pos降序 → 依次替换。

**为什么不能整段重写**：模板的下划线是**字符级 Underline 格式**（不是下划线字符）。用 `Range.Text` 覆盖整段会冲掉该段所有格式；正确做法是只覆盖**目标那几个字符**，Word会自动继承第一个字符的格式（下划线）。

## 五、模板版本变了怎么办

⚠ 模板一改，**字符下标会整体漂移，而生成流程不会报错** —— 只会静默填错位置、发出内容错位的意向书。所以必须走这三步：

```bash
cd scripts
# 1) dump 模板结构（自动落盘到 scripts/template-dump.txt）
powershell -NoProfile -ExecutionPolicy Bypass -File dump-template.ps1 -Template "<模板绝对路径>"
# 2) 机器解析槽位（比手抄可靠）
node parse-slots.js "<dump文件>" "<slots-xxx.json>"
# 3) 交叉校验 config.js 的 fills 是否仍与模板对齐
node verify-slots.js
```

`verify-slots.js` 输出形如：
```
✅ tech       16 条填位全部对齐
✅ sales      16 条填位全部对齐
✅ brand      17 条填位全部对齐
✅ other      17 条填位全部对齐
✅ expatriate 23 条填位全部对齐
共校验 89 条填位，0 处问题
```
**任何一条不一致都必须先修 config.js 再生成**。校验通过后同步更新 `config.js` 里的 `fingerprint`（Size / LastWriteTime）。

⚠ dump 脚本输出到控制台会有编码问题，**结果写文件再用 Read 读**（脚本已自动落盘）。

⚠ **JavaScript 注释是 `//` / `/* */`，不是 `#`**。用 `#` 写注释会报 `SyntaxError: Invalid or unexpected token`，且报错点在第 1 行——极易误判成编码或 BOM 问题（排查 wastes 很多时间）。
