# 链路二B / 三B · 社招录用意向书 + offer 发送

社招**同样要走录用意向书和 offer**，与校招共用模板体系，但**口径不同**。
本文只写与校招的差异点；链路二/三的通用步骤见 `workflow-intent.md` / `workflow-offer.md`。

## 前置条件

⚠ **必须等录用审批全部通过（审批人为 Neil 本人）后再开始**。审批未通过时：
- 意向书的入职日期、转正日期会与最终审批结果不一致 → 白做
- offer 表单此时还不能填（卡片上只有「撤销审批 / 催办」，没有「发送Offer」）

## 一、选模板：按固定部分比例，不是按「社招/校招」

社招与校招**用同一套模板**，判据是**岗位线的固定部分比例**：

| 岗位线 | 固定部分 | 模板 key |
|---|---|---|
| 职能 / 技术 / 研发 / 产品 / 技术支持 / 客户成功线 | 80/5/15 | `tech`（1-2 职能及技术类） |
| 销售线（含电销）、品牌营销线（平面设计师除外） | 95/5 | `sales`（1-1 销售通用类）/ `brand`（1-1 品牌营销类） |
| 其他未归类 | 80/5/13 | `other`（1-2 其他） |

**例：候选人A**（初级实施专员 / 营销序列 S1 / 远程实施组 / 客户成功线）
→ 不属于销售线也不属于品牌营销线 → 走 **通用 80/5/15** → 用 **`tech` 模板**（18×4，三项固定部分）。
→ 若误用 `sales` 模板，意向书会变成 95/5 且无绩效项，与审批表的 3600/225/675 冲突。

## 二、社招意向书的字段口径差异

| 字段 | 校招 | **社招** |
|---|---|---|
| 入职日期 | 2027/07/01（固定） | **录用审批里填的实际入职日**（2026/11/06） |
| 试用期 | 6 个月 | **销售 6 / 其他 3 个月**（与技术模板默认的 6 个月不同！） |
| 试用期收入 | ×85% | ×85%（同上，比例一致） |
| 转正后收入 | 8000 等 | **4500**（审批表的转正后满额） |
| 固定部分 | 80/5/15 或 95/5 | 同上，**按岗位线** |
| 首期合同期限 | 3年以上 + 合同终止年季度末 | 同算法（入职年+3，取同季度最后一天） |
| 联系人 | HR 联系人 | **按合同主体自动带出的那个**（福州誉龙 → <社招联系人姓名> / <社招联系人电话>） |
| 工作地点 | 福建福州及您参与的项目… | **按合同主体**：福州 → 福建福州；成都 → 成都 |
| 告知有效期 | 动态 | **同样动态**（N 天从发送当天起算含当天） |

⚠ **试用期月数是最容易漏的一项**：`tech` 模板 R7 原文是「试用期限为 **6** 个月」，
社招非销售岗要改成 **3** 个月（`texts` 里的 `probMonthsText` 替换）。

⚠ **联系人**：技术模板的联系人段在**表外段落 P77**（`您如有任何问题…(联系人：<HR联系人> 电话：<HR手机>)`），
**社招也保持模板原文的 HR 联系人**（Neil 2026-10-30 决定：与前 13 份校招保持一致，不改成审批表带出的那个）。
⇒ 技术模板**不需要**加 contact 替换规则，社招录用审批表里的联系人与意向书可以不一致（前者是系统字段，后者是意向书抬头）。

## 三、offer 表单的字段差异

社招的 offer 表单字段与校招**不同**，重点：

- 薪资是**转正前 + 转正后两套**（各 3 项），校招只有一套
- 有**合同主体**、**报到地址**、**录用类型**、**计薪方式** 等社招专属字段
- 抄送邮箱仍为 Neil 本人

### ⚠ 邮件模板必须选「正式员工 - 福州」，不能选「校招」

offer 表单预览页的「邮件模板」下拉有 4 个选项：

| 选项 | 适用 |
|---|---|
| **正式员工 - 福州** | **社招（合同主体 = 福州誉龙）** ← 社招用这个 |
| 正式员工 - 成都 | 社招（合同主体 = 成都先锋寰宇） |
| 实习员工 - 通用 | 实习生 |
| 校招 | **校招** |

⚠ **这是社招最容易错的一处**：默认值本来就是「正式员工 - 福州」，
但**主动选一次才可靠**（草稿不保存，不选/选错都不会报错，只是发错版本）。

**两个模板的正文差异（都实测过）**：

| | 正式员工 - 福州 | 校招 |
|---|---|---|
| 称呼 | `{#姓名}先生/女士 您好：` | `{#姓名}同学：` |
| 报到材料 | 含**离职证明**、**薪资证明**（上一家单位/近3个月流水）、社保卡公积金卡 | 无离职证明要求 |
| 税籍条款 | 含「**非中国国籍**公民，请提供国籍信息（直接影响个人收入缴税比例）」 | 无 |

⇒ 社招用校招模板，候选人**不会收到离职证明/薪资证明的要求**，且被叫「同学」。

**校验方法**（`send-offer-social.js` 已内置，违反即中止）：
读编辑器正文，断言「离职证明」「薪资证明」「上一家工作单位」「先生/女士」都在，
且**不含「同学」**。

**定位下拉的方法**：按 `.el-select` 里 **`input.value`** 匹配
（`正式员工|校招|实习`），**不要用 innerText** —— 实测该 el-select 的 innerText 为空，
用 `filter({ hasText: … })` 会匹配不到。

## 四、岗位 → 部门 → Leader 映射

社招的入职部门没有下拉（是组织架构树），必须按映射填。映射表在 `config.js` 的
`social.jobDeptMap`，每条包含：

```js
'初级实施专员': {
  dept: '远程实施组',                                    // 填进审批表
  fullPath: 'CS Dpt.(客户成功线)/Implementation(远程实施部)/远程实施组',
  seq: '营销序列-S', rank: 'S1',                         // 职级
  leader: '<远程实施组 Leader>',                               // 汇报对象
  pay: 'default',                                        // 指向 social.payStructure
}
```

**新增岗位时按同样结构补一条**，并把 `config.js` 的 `social.deptLeaders` 一并更新。

## 八、社招 offer 的两个隐藏要点

1. **「offer有效期」字段在「基础信息」区**（不在入职信息区），**默认值就是 3**。
2. **社招卡片可能有多张**（例：候选人A 有 1 张本人卡 + 2 张近似姓名的在人才库），
   必须按「应聘职位含关键字 **且** 有『发送Offer』按钮」双重匹配，否则选错人。

## 九、社招 offer 脚本

`$HIRE_WORKSPACE/send-offer-social.js`（从 `send-offer.js` 改造）

```bash
node send-offer-social.js <姓名> <岗位关键字> <意向书JPEG绝对路径>        # 停在发送前
node send-offer-social.js <姓名> <岗位关键字> <意向书JPEG绝对路径> --send # 发送
```

**与校招版的关键差异**：社招 offer 表单**已自动继承录用审批的值**
（入职日期 / 试用期 / 转正日期 / 薪酬 6 项 / 两个合计），所以脚本**不改入职日期**，
改成**只校验不改**（避免与审批不一致）。额外校验：offer有效期 = 3、两个薪酬合计 > 0。
其余（选抄送 → 预览 → 模板选校招 → 修改邮件 → 插图 → 确定 → 发送）完全复用校招逻辑。

### 邮件插图的验证办法

编辑器提交后 DOM 会清空，抓不到 img。**用日志里打印的 ptoken 下载**：

```js
const url = 'https://files.xinrenxinshi.com/site/download?ptoken=XXX';
// fetch → base64 → 存盘 → 本地打开核对
```
比截图可靠（页面有动画时 `screenshot` 必超时）。
